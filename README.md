# Curador CABA Intelligence

Observatorio ejecutivo del Boletín Oficial de la Ciudad Autónoma de Buenos Aires: normas, contrataciones públicas y un panel de "inteligencia" tecnológica/ciberseguridad derivado de esas contrataciones.

Es un dashboard **100% estático** (sin backend propio): un pipeline en Python recolecta y clasifica los datos, los publica como JSON dentro del mismo repo, y un frontend en HTML/JS los consume vía `fetch`. Todo el ciclo — scraping, clasificación, commit y deploy — corre solo, en GitHub Actions.

Dashboard en vivo: publicado vía GitHub Pages a partir de la rama `master` (ver `.github/workflows/pages.yml`).

## Arquitectura

```
Boletín Oficial CABA (API pública)
        │
        ▼
runtime/collector.py            → runtime/output/latest.json (no versionado)
        │  scrapea el boletín del día, dedup por id_norma
        ▼
runtime/data_model.py           → data/editions.json, data/norms.json,
        │  merge incremental contra el histórico,          data/procurements.json,
        │  detecta contrataciones y las clasifica            data/stats.json
        ▼
runtime/procurement_intelligence.py → data/procurement_intelligence.json
        │  etiqueta por tema (ciberseguridad, cloud, etc.) y vendors mencionados
        ▼
index.html + app.js + styles.css
        fetch() de los JSON de data/, todo el filtrado/render es client-side
```

`runtime/bac_catalog_collector.py` consume por separado el catálogo oficial de **Buenos Aires Compras (BAC)** — un dataset OCDS real (`data.buenosaires.gob.ar/dataset/buenos-aires-compras`, resource `bac_anual.csv`, OCDS aplanado) con adjudicaciones, montos y proveedores. Corre en su propio workflow diario (`refresh-bac-data.yml`), no en el de 30 min, porque el archivo pesa ~55MB y la fuente se actualiza con una cadencia de días/semanas, no minutos. Genera `data/bac_catalog.json` con un ranking de proveedores por monto adjudicado y un bloque `audit_signals` pensado para auditoría de compras de tecnología (ver más abajo).

**Por qué CSV y no el JSON homónimo**: el mismo `package_show` también expone `bac_anual.json` (mismo dataset, formato OCDS release package sin aplanar). Se descartó porque, verificado contra el CDN real, **ese JSON sólo contiene datos de enero-junio 2022** — se re-sube periódicamente (mismo `Last-Modified` que el CSV) pero su contenido nunca avanza. El CSV sí tiene datos reales con ~2-3 meses de atraso respecto a la fecha actual. Limitación del CSV a cambio: al ser OCDS *aplanado*, sólo trae el índice `0` de cada array (`awards/0/...`, `parties/0/...`) — si un award tuviera más de un proveedor (co-adjudicación), sólo se ve el primero.

**`bac_anual.csv` no es una fila = una adjudicación.** Verificado contra el CSV real completo (no es teórico): BAC emite una fila por cada combinación (renglón/ítem real, parte asociada — comprador, ente contratante, proveedor), así que sumar `awards/0/value/amount` fila por fila **duplicaba montos ~2.1x** en la primera versión de este pipeline. `dedupe_csv_rows()` en `bac_catalog_collector.py` colapsa las filas usando una clave derivada del propio campo `id` de la fila (renglón real) + `awards/0/items/0/id` — validada contra el dataset completo (0 inconsistencias de monto dentro de cada grupo resultante, en 14.937 grupos derivados de 24.911 filas). Ambigüedad residual conocida, no resuelta: en órdenes de compra de convenio marco con decenas/cientos de organismos habilitados a comprar de un mismo catálogo (misma fila de monto repetida una vez por organismo elegible), esta clave puede seguir sub-dividiendo por variantes del ítem sin que se pueda confirmar, sólo con el CSV aplanado, si cada una es una compra real distinta o una habilitación de catálogo — `award.csv` (otro recurso del mismo paquete CKAN) podría resolverlo, pero usa un esquema de `ocid` completamente distinto que no cruza contra `bac_anual.csv`, así que queda sin verificar.

## Datos (`data/`)

| Archivo | Contenido | Clave |
|---|---|---|
| `editions.json` | Historial de ediciones del Boletín Oficial recolectadas | `numero_boletin` |
| `norms.json` | Todas las normas vistas hasta el momento (acumulativo) | `id_norma` |
| `procurements.json` | Subconjunto de `norms.json` detectado como contratación | `id_norma`, agrupable por `proceso_id`; `bac_tender_id` cuando el sumario cita el número de proceso de BAC |
| `procurement_intelligence.json` | `procurements.json` enriquecido con tags temáticos y vendors mencionados | — |
| `normative_impact.json` | Normas de Jefatura de Gabinete de Ministros publicadas por unidades de sistemas/transformación digital (Secretaría de Innovación y Transformación Digital, Agencia de Sistemas de Información y direcciones asociadas), identificadas por la sigla del acto | — |
| `stats.json` | Métricas agregadas que consume el panel principal del dashboard | — |
| `sync_manifest.json` | Metadata de la última sincronización pública (para el badge de estado) | — |
| `bac_catalog.json` | Adjudicaciones reales de Buenos Aires Compras (OCDS): ranking de proveedores por monto, señales de auditoría en tecnología y `tender_index` (agregado por proceso de BAC, ver cruce por expediente) | `tender_index` clave es el número de proceso de BAC (ej. `416-1192-LPU26`) |
| `bac_sync_state.json` | ETag/Last-Modified del recurso BAC en la última corrida, para no re-descargar ~55MB si no cambió | — |
| `bac_aperturas.json` | Radar en tiempo (casi) real de licitaciones en apertura y próximas a abrir, scrapeado del sitio transaccional de BAC | 30 min (horario administrativo) |
| `bac_pliegos_caidos.json` | Pliegos de tecnología declarados Desierto o Dejado Sin Efecto, scrapeados en vivo de la Búsqueda avanzada del sitio transaccional de BAC (no del export masivo trimestral) | 1h (horario administrativo) |
| `bac_recurring_vendor_watch.json` | Chequeo en vivo, para candidatos identificados en `bac_catalog.json.audit_signals.recurring_direct_pairs`, de si un organismo+proveedor con adjudicaciones directas repetidas siguió ganando por vía directa más allá de lo que cubre `bac_anual.csv` | diaria |

**Auditoría de compras de tecnología (`bac_catalog.json.audit_signals`):** el objetivo del dashboard es facilitar auditoría, no sólo mostrar métricas. BAC no publica `numberOfTenderers`/`tenderers` (confirmado: 0 ocurrencias en todo el dataset), así que la única señal de competencia real que expone el propio publicador es el booleano `tender.competitive`. Sobre eso se calculan cinco señales, todas acotadas a contrataciones clasificadas como tecnología:
- `direct_or_limited_share_pct`: % del monto adjudicado por contratación directa/limitada en vez de licitación pública.
- `non_competitive_open_tenders`: licitaciones formalmente públicas (`procurementMethod=open`) que BAC marca como sin competencia real (`competitive=false`) — en la corrida de referencia esto fue el **54% del monto adjudicado en tecnología**, la señal más fuerte encontrada hasta ahora.
- `vendor_concentration_by_organismo`: organismos donde un solo proveedor se lleva ≥60% de su gasto en tecnología (con un piso de $1M para no marcar compras únicas chicas como "concentración"). Sin tope de cantidad — expone todos los organismos que califican, no sólo los primeros N, porque el frontend lo usa además para buscar por nombre (ver "Cruce Boletín↔BAC por organismo" más abajo). El frontend renderiza el ranking completo ordenado por monto (no sólo por el top-8 de organismos más activos en el Boletín), para que un hallazgo grande en un organismo poco activo en normas no quede oculto.
- `possible_fractionation`: organismo+proveedor con 3 o más adjudicaciones directas/de contratación limitada en una ventana de hasta 90 días (`FRACTIONATION_MIN_AWARDS`/`FRACTIONATION_WINDOW_DAYS` en `bac_catalog_collector.py`). No conocemos el umbral legal exacto de contratación directa de CABA desde este dataset, así que en vez de inventar un monto la señal marca el patrón de repetición — disparador de revisión de posible fraccionamiento, no una acusación.
- `repeat_winner_across_organismos`: el mismo proveedor con adjudicaciones directas/limitadas en 3 o más **organismos distintos** en una ventana de hasta 90 días (`REPEAT_WINNER_MIN_ORGANISMOS`/`REPEAT_WINNER_WINDOW_DAYS`). Complementa la señal anterior mirando la otra dimensión — no "mismo comprador, mismo proveedor, muchas veces" sino "mismo proveedor, muchos compradores distintos, rápido" — un patrón que `vendor_concentration_by_organismo` no puede ver porque mira un organismo a la vez. Con la ventana de datos actual (~5 meses, sólo 15 proveedores con adjudicaciones directas/limitadas en tecnología) no hay ningún proveedor que la dispare todavía; queda lista para cuando la cobertura temporal crezca.
- `recurring_direct_pairs`: organismo + proveedor con `RECURRING_PAIR_MIN_AWARDS` (2) o más adjudicaciones directas/limitadas, **sin ventana de tiempo** — a diferencia de `possible_fractionation`, que exige que se agrupen en 90 días. Mira una relación de largo plazo (posible renovación informal de un contrato por vía directa en vez de re-licitar), no una ráfaga puntual. Es la lista de candidatos que consume `bac_recurring_vendor_watch.py` (ver más abajo) para el chequeo en vivo.

Ninguna de estas señales prueba irregularidad por sí sola — son disparadores para que un auditor priorice qué expediente revisar primero, no un veredicto.

**Proveedor recurrente por contratación directa, en vivo (`bac_recurring_vendor_watch.json`):** enriquecimiento acotado del ítem "prórrogas encubiertas / contrataciones directas por urgencia" del roadmap. `bac_anual.csv` sí tiene identidad de proveedor (a diferencia de la grilla de resultados de `BuscarAvanzado.aspx`, que no la expone — confirmado navegando el sitio real), pero está ~3 meses atrasado; la Búsqueda avanzada del sitio transaccional sí está al día. Estrategia: no escanear todo BAC en vivo (inviable — sólo Contratación Directa + Informática + Adjudicado ya son 10+ páginas de historial), sino usar `recurring_direct_pairs` de `bac_catalog.json` como lista de candidatos (universo chico hoy: 3, mismo motivo que `repeat_winner_across_organismos` no dispara nada todavía — `bac_anual.csv` sólo cubre unos meses) y, para cada uno, buscar en vivo si el organismo tuvo una adjudicación directa **más reciente que `coverage.date_to`** — y sólo si la hay, confirmar la identidad del proveedor visitando el detalle del proceso (`VistaPreviaPliegoCiudadano.aspx`, tabla "Orden de compra": `Nombre proveedor`, CUIT, fecha, monto) antes de marcarlo. Ese último paso es deliberado: mismo organismo no alcanza, podría ser un proveedor distinto ganando por primera vez — sin confirmarlo sería un falso positivo. `runtime/bac_recurring_vendor_watch.py` reusa `read_grid_rows`/`click_next_page`/`parse_row` de `bac_pliegos_caidos_scraper.py` (mismo patrón de grilla+paginador, genérico) y `split_unidad_ejecutora`/`parse_fecha_apertura` de `bac_aperturas_scraper.py`. La normalización de nombres (`normalize_name`, mismo criterio que `normalizeOrgName` en `app.js`) es deliberadamente estricta — prefiere un falso negativo (no confirmar un match real) a un falso positivo. Corre diario (no horario: el universo de candidatos casi no cambia entre corridas de `refresh-bac-data.yml`, también diaria) en `refresh-bac-recurring-vendor-watch.yml`. Es esperable "sin resultados" la mayor parte del tiempo, mismo criterio que `repeat_winner_across_organismos`.

**Pliegos caídos o fracasados, en vivo (`bac_pliegos_caidos.json`):** esta señal empezó viviendo en `bac_catalog.json.audit_signals` (`tender.status` en `cancelled`/`unsuccessful` sobre `bac_anual.csv`), pero se migró a un scraper separado (`runtime/bac_pliegos_caidos_scraper.py`) porque el export masivo de BA Data quedó demasiado atrasado para esta señal en particular: verificado con `HEAD` contra el CDN, **los 8 archivos del dataset `buenos-aires-compras`** (tender.csv, award.csv, contracts.csv, bac_anual.csv/json/xlsx, bac.csv) **comparten el mismo `Last-Modified`**, congelado desde que BA Data regeneró el paquete completo por última vez — no es un problema de qué archivo del paquete se elige, es que el paquete entero no se re-genera seguido. El sitio transaccional de BAC, en cambio, expone una "Búsqueda avanzada" (`BuscarAvanzado.aspx`) que pega contra la base real: filtrando `Estado de Proceso` = Desierto/Dejado Sin Efecto y `Rubro` = Informática (ambos nativos del sitio, más precisos que reclasificar por regex) aparecen pliegos con fecha de apertura de semanas atrás, no meses. Mismo patrón de navegación que `bac_aperturas_scraper.py` (click real desde `Default.aspx`, ver limitaciones conocidas), reutilizando sus funciones puras de parseo (`split_unidad_ejecutora`, `parse_fecha_apertura`). Corre en el mismo workflow y cadencia que las aperturas (`refresh-bac-aperturas.yml`). Como el filtro de fecha del formulario no resultó confiable de automatizar (se vació el campo en vez de aplicar el rango, posible validación de formato del lado del cliente), el scraper trae el universo completo de Estado+Rubro (chico: ~2-3 páginas por estado) y lo ordena por fecha descendente, en vez de acotar por rango — el frontend muestra los primeros 15.

**Impacto normativo en sistemas (`normative_impact.json`):** además de `bac_catalog.json` (contratación), `runtime/normative_impact.py` mira `norms.json` completo para detectar normas que puedan modificar circuitos digitales de la Ciudad. El campo `organismo` no sirve para esto por sí solo: casi 600 normas de Jefatura de Gabinete de Ministros comparten el mismo valor genérico de `organismo` ("Jefatura de Gabinete de Ministros"), sin distinguir qué unidad real las dictó. La unidad real está codificada como sigla en el número de acto (ej. `Disposición N° 24/DGISIS/26` → sigla `DGISIS`), así que la detección filtra por esa sigla contra una lista curada de unidades de sistemas/transformación digital (`SYSTEMS_SIGLAS` en el script: `SECITD`, `ASINF`, `DGISIS`, `DGIASINF`, `DGTALINF`, `DGGEDOC` — confirmadas contra fuentes oficiales o, en el caso de las tres últimas, contra el patrón real de uso en el Boletín, no adivinadas). Es deliberadamente conservador: `DGIUR`, la sigla más frecuente de JGM en el dataset (376/566 normas), es Interpretación Urbanística y queda afuera a propósito — incluir cualquier sigla de JGM sin verificar a qué unidad corresponde generaría ruido, no señal. Sobre las normas que matchean, se aplican tags de texto libre best-effort (`GDE`/`TAD`, firma digital, ciberseguridad, interoperabilidad, plataforma/sistema) — de cobertura baja a propósito, porque `nombre`/`sumario` son el título/resumen del Boletín, no el cuerpo completo de la resolución (considerandos/articulado), que no se recolecta. **Limitación importante:** esto señala que una norma *puede* afectar circuitos digitales; no identifica automáticamente qué procedimiento puntual modifica (para eso haría falta el texto completo de la resolución y un mapeo de procedimientos, que no existen en este dataset) — es un disparador para revisión manual, no una alerta accionable por sí sola.

**Redeterminaciones de precio reiteradas (`normative_impact.json.price_redeterminations`):** señal derivada del mismo conjunto de normas de unidades de sistemas. Las disposiciones de aprobación de actualización de precios de una Orden de Compra declaran el ordinal en texto plano (ej. "Aprueba la **Novena** Actualización de Precios de la Orden de Compra N° 8056-0106-OCA25" → 9ª redeterminación de esa orden) — confirmado contra datos reales, lo que hace viable esta señal **sin** reconstruir un historial de montos (que no existe en ningún dataset disponible acá, ni en `bac_anual.csv` ni en el sitio transaccional). `extract_price_redetermination` parsea ese ordinal (sólo formas simples 1ª-10ª: `ORDINALS` en el script; ordinales compuestos como "Décimo Primera" no se parsean, limitación documentada, no un bug) y `build_price_redetermination_flags` marca las que llegan a `REDETERMINATION_MIN_ORDINAL` (3, arbitrario y documentado como tal — 1-2 redeterminaciones en un contrato largo es un mecanismo contractual normal, no una señal). No implica irregularidad por sí sola — es un disparador para revisar el contrato subyacente cuando la misma orden se redetermina muchas veces seguidas.

**Cruce Boletín↔BAC por organismo:** el cruce por número de proceso propio de cada fuente no es viable directamente (esquemas de numeración distintos — ver el cruce por expediente más abajo, que sí funciona por otra vía), pero **los nombres de organismo sí son comparables** entre ambas fuentes una vez normalizados (mayúsculas, sin acentos, sin puntos). `app.js` (`normalizeOrgName`, `bacOrgIndex`) cruza el ranking de organismos del Boletín contra `vendor_concentration_by_organismo` de BAC: si un organismo del Boletín tiene una coincidencia de nombre normalizado en BAC, se le agrega un badge de alerta (⚠ BAC) en el ranking. Es un cruce **best-effort por nombre exacto normalizado, no fuzzy** — organismos que BAC nombra en forma abreviada (ej. "HTAL. RICARDO GUTIERREZ") no matchean su forma larga en el Boletín si difieren. Alta precisión, cobertura parcial.

**Cruce Boletín↔BAC por expediente (`bac_tender_id` / `tender_index`):** aunque el Boletín identifica el proceso por sigla+año (`14/IVC/26`, ver `proceso_id`) y BAC por su propio código de organismo+secuencial+tipo (`416-1192-LPU26`, ver `numero_proceso` en `bac_aperturas.json`), **el sumario del Boletín suele citar el número de proceso de BAC como texto libre además de la sigla** — confirmado contra datos reales: ~70% de `procurements.json` trae ese patrón embebido en `nombre`+`sumario`, y de las aperturas actualmente listadas en `bac_aperturas.json`, más de la mitad matchean exacto contra un `id_norma` del Boletín por esta vía. `data_model.py` (`bac_tender_id`) extrae ese ID del texto y lo guarda como campo en cada registro de `procurements.json`; `bac_catalog_collector.py` extrae el mismo ID desde la columna `id` del CSV (que lo trae como prefijo, ej. `416-1192-LPU26-16-0` → renglón 16, parte 0 — ver `dedupe_csv_rows`) y publica un índice agregado por proceso en `bac_catalog.json.tender_index` (acotado a tecnología, mismo criterio que el resto de `audit_signals`). Es una clave de cruce más precisa que la de organismo (matchea el expediente puntual, no sólo "algún proceso de este organismo"), pero de cobertura parcial (no todo `sumario` cita el ID de BAC) — pendiente: consumir `tender_index` desde el frontend para mostrar el cruce por expediente en el explorador de "Procesos" (hoy sólo existe a nivel de pipeline).

**Actos vs. procesos:** una misma licitación puede generar varios actos publicados (llamado, circulares, prórroga), cada uno con su propio `id_norma`. `stats.procurement_acts` cuenta actos individuales; `stats.procurements` cuenta **procesos únicos** (agrupados por `proceso_id`, extraído del número de expediente citado en el nombre de la norma, ej. `14/IVC/26`). El dashboard y las métricas de categoría usan el conteo por proceso para no inflar el número de contrataciones reales. En la sección "Procesos" del explorador, los actos de un mismo expediente se agrupan visualmente: el acto principal se muestra siempre, y los relacionados (circulares, prórroga) quedan plegados bajo un `<details>` expandible.

## Automatización (GitHub Actions)

- **`refresh-official-data.yml`**: corre cada hora en horario hábil (11:00–16:00 UTC / 08:00–13:00 ART, lunes a viernes; bajado de cada 30 min porque GitHub empezó a demorar/descartar disparos de `schedule` de alta frecuencia) más una corrida extra a las 12:55 ART. Ejecuta el pipeline del Boletín (`collector.py` → `data_model.py` → `procurement_intelligence.py` → `normative_impact.py`), valida que los JSON de salida sean válidos, commitea los cambios con el bot `caba-dashboard[bot]` y dispara el deploy a Pages. También se puede disparar manualmente (`workflow_dispatch`) o al tocar algo en `runtime/`.
- **`refresh-bac-data.yml`**: corre 1 vez por día a las 06:00 UTC (03:00 ART, fuera de la ventana del refresh de 30 min). Descarga y parsea `bac_anual.csv` sólo si cambió (chequeo condicional por ETag/Last-Modified), y hace commit+deploy igual que el workflow del Boletín. Ambos workflows comparten el mismo `concurrency.group` (`caba-dashboard-refresh`) para que nunca corran en paralelo y se pisen el push a `master`; además, los dos hacen `git fetch && git rebase` antes de pushear como defensa adicional (en `refresh-bac-data.yml` un conflicto de rebase se resuelve automáticamente a favor de la corrida actual, porque `bac_catalog.json` siempre es una regeneración completa, no un merge incremental).
- **`refresh-bac-aperturas.yml`**: cada hora en el mismo horario administrativo que el Boletín (11:00-16:00 UTC, lunes a viernes — bajado de cada 30 min por el mismo motivo de throttling de GitHub). Instala Chromium (`playwright install --with-deps chromium`) y corre `runtime/bac_aperturas_scraper.py` y `runtime/bac_pliegos_caidos_scraper.py`, que navegan el sitio transaccional de BAC con un navegador headless real (ver limitaciones conocidas más abajo). Mismo patrón de auto-resolución de conflictos de rebase que `refresh-bac-data.yml` (ambos JSON son regeneración completa cada corrida), con `GIT_EDITOR=true` explícito en el fallback de `rebase --continue` para no colgarse sin TTY.
- **`refresh-bac-recurring-vendor-watch.yml`**: 1 vez por día a las 08:00 UTC (después de `refresh-bac-data.yml`, para trabajar sobre candidatos frescos). No corre horario como los otros scrapers del sitio transaccional porque el universo de candidatos (`recurring_direct_pairs`) casi no cambia entre corridas diarias — scrapearlo cada hora desperdiciaría carga sobre el sitio de BAC sin ningún beneficio real. Mismo patrón de Playwright + auto-resolución de conflictos que `refresh-bac-aperturas.yml`.
- **`backfill-boletin.yml`**: sólo `workflow_dispatch` (sin cron) — rellena ediciones históricas del Boletín que el pipeline diario nunca capturó, vía `runtime/backfill_boletin.py`. Inputs `start`/`end` (número de boletín); `end` vacío calcula automáticamente "justo antes de la edición más antigua ya capturada", para no crear huecos ni pisar nada al reintentar. ~30-50s por edición medido en pruebas reales — para rangos grandes (decenas/cientos de ediciones) puede tardar horas, por eso `timeout-minutes: 240`. Comparte el mismo `concurrency.group` que los demás workflows; a diferencia de `refresh-bac-data.yml`, **no** auto-resuelve conflictos de rebase (mismo criterio que `refresh-official-data.yml`: es merge incremental, no regeneración completa, así que ante un conflicto real se prefiere fallar para revisión manual).
- **`pages.yml`**: deploya el contenido del repo a GitHub Pages en cada push a `master`.

## Desarrollo local

Requisitos: Python 3.12+, sin dependencias de frontend (no hay build step).

```bash
# pipeline de datos
python -m venv .venv && source .venv/bin/activate
pip install -r runtime/requirements.txt

python runtime/collector.py               # pega contra la API oficial, genera runtime/output/latest.json
python runtime/data_model.py              # actualiza data/editions.json, norms.json, procurements.json, stats.json
python runtime/procurement_intelligence.py  # genera data/procurement_intelligence.json
python runtime/normative_impact.py          # genera data/normative_impact.json (impacto normativo en sistemas)
python runtime/bac_catalog_collector.py     # descarga y parsea BAC (~55MB), genera data/bac_catalog.json
```

```bash
# frontend — cualquier servidor estático sirve, por ejemplo:
python -m http.server 8000
# abrir http://localhost:8000
```

Variable de entorno soportada por el collector: `CABA_BO_BASE` (default `http://api-restboletinoficial.buenosaires.gob.ar`), útil para apuntar a un mock/entorno alternativo en tests manuales.

## Tests

```bash
python -m unittest discover -s runtime/tests -v
```

Cubren las funciones puras del pipeline (`isproc`, `category`, `proceso_id`, `merge_norm`, `belongs`, y todo `bac_catalog_collector.py`: clasificación tecnología, resolución de proveedores, señales de auditoría, detección de cambios; y todo `normative_impact.py`: extracción de sigla, filtro por organismo, clasificación de tópicos) — son el código con más riesgo de regresión porque dependen de heurísticas de texto sobre APIs externas no documentadas oficialmente.

## Limitaciones conocidas / roadmap

- Todo el estado vive en JSON commiteados a git (patrón "git como base de datos"); funciona para el volumen actual pero es el primer punto a rediseñar si esto se migra a un runtime propio (ej. Cloud Run Jobs + Cloud SQL/Firestore en GCP).
- La clasificación por categoría/tema es rule-based (regex sobre texto libre) — precisa pero no perfecta; ver `runtime/data_model.py` (`category`) y `runtime/procurement_intelligence.py` (`RULES`) antes de confiar ciegamente en los conteos por rubro.
- Sin tests para `collector.py` más allá de `belongs()` (el resto depende de la forma real de la respuesta de la API oficial, no reproducible sin fixtures grabadas).
- **`bac_anual.csv` tiene ~2-3 meses de atraso respecto a la fecha actual** (no es en tiempo real; la ficha del dataset no garantiza una cadencia fija — "trimestral" según CKAN, "cada 15 días" según documentación histórica de BAC_OCDS). `bac_catalog.json.coverage` expone el rango real de fechas procesado en cada corrida; no asumir que son datos del día sin chequearlo ahí. Esta limitación afecta a **todas** las señales de `bac_catalog.json` (concentración, fraccionamiento, etc.) — la única señal que ya no depende de este export es "pliegos caídos", migrada a un scraper en vivo (ver `bac_pliegos_caidos.json` más arriba) precisamente por este motivo.
- Las señales de auditoría (`audit_signals`) son heurísticas con umbrales documentados pero arbitrarios (`CONCENTRATION_MIN_AMOUNT`, `CONCENTRATION_HIGH_PCT` en `bac_catalog_collector.py`) — son disparadores para revisión manual, no una conclusión de irregularidad.
- El cruce Boletín↔BAC **por nivel de organismo** y, ahora también, **por expediente** (`bac_tender_id`/`tender_index`, ver arriba) ya están implementados a nivel de pipeline. Pendiente: consumirlo desde `app.js` para mostrar el badge de cruce por expediente en el explorador de "Procesos" (hoy sólo existe el badge por organismo). También pendiente el caso que el cruce por expediente todavía no cubre: detectar licitaciones publicadas en el Boletín que nunca aparecen adjudicadas en BAC (o viceversa) cuando el sumario no cita el ID de BAC en texto libre — ahí sí seguiría haciendo falta un mapeo sigla↔código de organismo, que no existe hoy.
- **`norms.json` creció a ~65MB tras el backfill histórico del Boletín** (`runtime/backfill_boletin.py`, disparable manualmente vía `.github/workflows/backfill-boletin.yml` — reutilizable a futuro para rellenar huecos puntuales de ediciones no capturadas). Es un salto único para tener paridad de ventana temporal con BAC, no un crecimiento recurrente; si se repite (más backfills, ventanas más largas), habrá que particionar `norms.json` por año/período en vez de mantenerlo como un solo archivo que el frontend descarga entero en cada visita (`fetch(..., {cache:'no-store'})` no cachea nada hoy).
- **Radar de aperturas en tiempo real (`bac_aperturas.json`)**: se intentó primero con `requests` puro contra el sitio transaccional de BAC (no el portal de datos abiertos), replicando fielmente una request real capturada del navegador (mismo HAR: headers, Referer, Origin, orden de campos, CSRF token) — siguió fallando con un redirect de sesión inválida. Es una página ASP.NET WebForms donde el ViewState/postback se genera con el estado real de la sesión, así que un replay de headers no alcanza. **Sí funciona con un navegador headless real** (`runtime/bac_aperturas_scraper.py`, Playwright): la clave no es sólo usar un navegador, sino navegar *como usuario real* — cargar `Default.aspx` y hacer click en el link real de cada listado (no pegarle directo a la URL, que igual redirige incluso con browser real) para que el postback se genere con el ViewState correcto. Corre cada 30 min en horario administrativo (`refresh-bac-aperturas.yml`), con Chromium instalado vía `playwright install --with-deps` en el runner. **El objeto de auditoría de este dashboard es tecnología, no toda la actividad de BAC**: el scraper guarda todas las aperturas (con un flag `is_technology` calculado con el mismo `classify_technology()` que usa `bac_catalog_collector.py`, sobre el único texto disponible en esa página — `nombre_proceso`, sin descripción separada), pero el frontend sólo lista las de tecnología, mostrando el total sin filtrar únicamente como contexto de cobertura. La mayoría de las aperturas reales son insumos médicos/obra/etc., así que este panel puede legítimamente mostrar "sin aperturas de tecnología" la mayor parte del tiempo — eso es correcto, no un error.
